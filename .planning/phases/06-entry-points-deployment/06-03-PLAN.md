**1. Add Cache-Control header to requireAuth middleware (`src/middleware/auth.ts`):**

In the `requireAuth` function, add `res.setHeader('Cache-Control', 'private, no-store');` immediately BEFORE the `req.user = user;` and `next();` lines (in the success path only — the 401 error paths don't need it since they're not returning cached-worthy data, but adding it there too is harmless).

Specifically, insert the line at approximately line 87-88 of the current file, right before `req.user = user;`:
```typescript
res.setHeader('Cache-Control', 'private, no-store');
req.user = user;
next();
```

This single change gives every route using `requireAuth` the header automatically — no per-route changes needed. Routes affected: POST /api/communities/:id/threads, POST /api/threads/:id/posts, PATCH /api/threads/:id, PATCH /api/posts/:id, GET /api/users/:id/posts, and all future auth-gated routes.

**2. Bundle scan for secrets:**

Run a fresh frontend build and scan the output:
```bash
cd frontend && npm run build
grep -r "service_role" dist/assets/ || echo "CLEAN: no service_role found"
grep -r "SUPABASE_SERVICE\|SUPABASE_KEY" dist/assets/ || echo "CLEAN: no SUPABASE_KEY found"
```

Expected result: No matches (clean). If any match is found, investigate which env var leaked through Vite and fix the `vite.config.ts` — but the research confirmed the bundle is currently clean.

**3. RLS anon/authenticated verification (against production):**

Run these curl commands against the live production URL to verify RLS behavior:
```bash
# Anon reads should work (200):
curl -s -o /dev/null -w "%{http_code}" https://fc.empowered.vote/api/communities
curl -s -o /dev/null -w "%{http_code}" https://fc.empowered.vote/api/health

# Auth-gated writes should reject (401 without token):
curl -s -o /dev/null -w "%{http_code}" -X POST https://fc.empowered.vote/api/communities/00000000-0000-0000-0000-000000000000/threads -H "Content-Type: application/json" -d '{"title":"test","body":"test body here"}'

# New post history endpoint should reject (401 without token):
curl -s -o /dev/null -w "%{http_code}" https://fc.empowered.vote/api/users/00000000-0000-0000-0000-000000000000/posts
```

Expected: 200 for reads, 401 for writes and post history.

**4. Verify Cache-Control header on production (after deploy):**

After the code with Cache-Control is deployed, verify with:
```bash
curl -s -I -X POST https://fc.empowered.vote/api/communities/00000000-0000-0000-0000-000000000000/threads -H "Content-Type: application/json" -H "Authorization: Bearer invalid" -d '{"title":"test","body":"test"}'
```
Note: This will return 401 (invalid token), but if the header is set before the auth check fails, it may or may not appear on 401 responses. The definitive test requires a valid token — that's done in the human-verify checkpoint below.

**5. Health endpoint verification:**
