<objective>
Create RLS policies on all connect.* tables (with WITH CHECK on every INSERT/UPDATE), schema grants for anon and authenticated roles, policy column indexes, and security-invoker views for published_posts and published_replies.

Purpose: This is the security layer. Without correct RLS policies, the database is open. Without grants, the connect schema is inaccessible. Without security_invoker views, RLS is silently bypassed. This plan locks down the schema created in Plan 01-02 before any application code touches it.

Output: Two migration files -- one for RLS policies + grants + indexes, one for security-invoker views.
</objective>

  <name>Task 1: Create RLS policies, schema grants, and policy column indexes migration</name>
  <files>supabase/migrations/TIMESTAMP_connect_schema_rls.sql</files>
  <action>
    Run `npx supabase migration new connect_schema_rls` to create the migration file.

    Write the following SQL into the generated file. CRITICAL: Use `(SELECT auth.uid())` (with SELECT wrapper) in EVERY policy expression -- never bare `auth.uid()`.

    **1. Schema grants (must come before policies that reference roles):**
    ```sql
    -- Grant schema access
    GRANT USAGE ON SCHEMA connect TO anon, authenticated;

    -- anon: read only on all current tables
    GRANT SELECT ON ALL TABLES IN SCHEMA connect TO anon;

    -- authenticated: read + write (RLS further restricts which rows)
    GRANT SELECT, INSERT, UPDATE ON ALL TABLES IN SCHEMA connect TO authenticated;

    -- Future tables get the same grants automatically
    ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA connect
      GRANT SELECT ON TABLES TO anon;
    ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA connect
      GRANT SELECT, INSERT, UPDATE ON TABLES TO authenticated;
    ```

    **2. RLS policies for connect.communities:**
    Communities are read-only for all users in v1 (populated by admin/seed). No INSERT/UPDATE policies needed yet.
    ```sql
    CREATE POLICY "communities_select_all"
    ON connect.communities FOR SELECT
    TO anon, authenticated
    USING (true);  -- all communities visible; no moderation_status filter needed (communities are admin-managed)
    ```

    **3. RLS policies for connect.threads:**
    ```sql
    -- Anyone can read visible threads
    CREATE POLICY "threads_select_visible"
    ON connect.threads FOR SELECT
    TO anon, authenticated
    USING (moderation_status = 'visible');

    -- Authenticated users insert their own threads only
    CREATE POLICY "threads_insert_own"
    ON connect.threads FOR INSERT
    TO authenticated
    WITH CHECK ((SELECT auth.uid()) = author_id);

    -- Authors can update their own visible threads
    CREATE POLICY "threads_update_own"
    ON connect.threads FOR UPDATE
    TO authenticated
    USING ((SELECT auth.uid()) = author_id AND moderation_status = 'visible')
    WITH CHECK ((SELECT auth.uid()) = author_id);
    ```

    **4. RLS policies for connect.posts:**
    ```sql
    -- Anyone can read visible posts
    CREATE POLICY "posts_select_visible"
    ON connect.posts FOR SELECT
    TO anon, authenticated
    USING (moderation_status = 'visible');

    -- Authenticated users insert their own posts only
    CREATE POLICY "posts_insert_own"
    ON connect.posts FOR INSERT
    TO authenticated
    WITH CHECK ((SELECT auth.uid()) = author_id);

    -- Authors can update their own visible posts
    CREATE POLICY "posts_update_own"
    ON connect.posts FOR UPDATE
    TO authenticated
    USING ((SELECT auth.uid()) = author_id AND moderation_status = 'visible')
    WITH CHECK ((SELECT auth.uid()) = author_id);
    ```

    **5. RLS policies for connect.thread_edits:**
    Edit history is publicly readable (memory over moderation). No INSERT/UPDATE by users (triggers only).
    ```sql
    CREATE POLICY "thread_edits_select_all"
    ON connect.thread_edits FOR SELECT
    TO anon, authenticated
    USING (true);
    ```

    **6. RLS policies for connect.post_edits:**
    ```sql
    CREATE POLICY "post_edits_select_all"
    ON connect.post_edits FOR SELECT
    TO anon, authenticated
    USING (true);
    ```

    **7. RLS policies for public.connected_profiles:**
    ```sql
    -- Anyone can read profiles (display names are public)
    CREATE POLICY "profiles_select_all"
    ON public.connected_profiles FOR SELECT
    TO anon, authenticated
    USING (true);

    -- Users can only insert their own profile
    CREATE POLICY "profiles_insert_own"
    ON public.connected_profiles FOR INSERT
    TO authenticated
    WITH CHECK ((SELECT auth.uid()) = user_id);

    -- Users can only update their own profile
    CREATE POLICY "profiles_update_own"
    ON public.connected_profiles FOR UPDATE
    TO authenticated
    USING ((SELECT auth.uid()) = user_id)
    WITH CHECK ((SELECT auth.uid()) = user_id);
    ```

    **8. Indexes on all policy columns (CRITICAL: in same migration as policies):**
    ```sql
    -- Threads indexes
    CREATE INDEX idx_threads_author_id ON connect.threads(author_id);
    CREATE INDEX idx_threads_community_id ON connect.threads(community_id);
    CREATE INDEX idx_threads_moderation_status ON connect.threads(moderation_status);

    -- Posts indexes
    CREATE INDEX idx_posts_thread_id ON connect.posts(thread_id);
    CREATE INDEX idx_posts_author_id ON connect.posts(author_id);
    CREATE INDEX idx_posts_parent_post_id ON connect.posts(parent_post_id);
    CREATE INDEX idx_posts_moderation_status ON connect.posts(moderation_status);

    -- Thread edits indexes
    CREATE INDEX idx_thread_edits_thread_id ON connect.thread_edits(thread_id);

    -- Post edits indexes
    CREATE INDEX idx_post_edits_post_id ON connect.post_edits(post_id);

    -- Communities indexes
    CREATE INDEX idx_communities_topic_id ON connect.communities(topic_id);
    CREATE INDEX idx_communities_slug ON connect.communities(slug);

    -- Connected profiles indexes
    CREATE INDEX idx_connected_profiles_user_id ON public.connected_profiles(user_id);
    ```
    Note: Some of these columns already have UNIQUE constraints which create implicit indexes (communities.slug, connected_profiles.user_id). The explicit indexes on those columns are harmless but can be omitted if preferred -- the important thing is that author_id, community_id, thread_id, moderation_status, and parent_post_id all have explicit indexes.

<task type="auto">
  <name>Task 2: Create security-invoker views migration</name>
  <files>supabase/migrations/TIMESTAMP_connect_schema_views.sql</files>
  <action>
    Run `npx supabase migration new connect_schema_views` to create the migration file.

    Write the following SQL into the generated file:

    **1. published_posts view (all visible posts -- both top-level and replies):**
    ```sql
    CREATE VIEW connect.published_posts
    WITH (security_invoker = true) AS
    SELECT
      p.id,
      p.thread_id,
      p.parent_post_id,
      p.author_id,
      p.author_display_name,
      p.body,
      p.created_at,
      p.updated_at,
      p.moderation_status
    FROM connect.posts p
    WHERE p.moderation_status = 'visible';
    ```
    CRITICAL: `WITH (security_invoker = true)` is mandatory. Without it, the view runs as the postgres superuser and bypasses all RLS policies.

    **2. published_replies view (only replies -- parent_post_id IS NOT NULL):**
    ```sql
    CREATE VIEW connect.published_replies
    WITH (security_invoker = true) AS
    SELECT
      p.id,
      p.thread_id,
      p.parent_post_id,
      p.author_id,
      p.author_display_name,
      p.body,
      p.created_at,
      p.updated_at
    FROM connect.posts p
    WHERE p.moderation_status = 'visible'
      AND p.parent_post_id IS NOT NULL;
    ```

    **3. Grant SELECT on views to anon and authenticated:**
    ```sql
    GRANT SELECT ON connect.published_posts TO anon, authenticated;
    GRANT SELECT ON connect.published_replies TO anon, authenticated;
    ```

    - Verify both views filter on `moderation_status = 'visible'`
