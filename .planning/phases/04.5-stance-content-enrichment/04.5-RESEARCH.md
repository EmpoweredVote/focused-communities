# Phase 4.5: Stance Content Enrichment - Research

**Researched:** 2026-04-16
**Domain:** PostgreSQL schema extension (inform.* shared schema) + supabase-js update pattern + RPC function contract update + authored seed content for civic stances
**Confidence:** HIGH

---

## Summary

Phase 4.5 has three distinct concerns: (1) a schema migration that adds two columns to `inform.compass_stances`, (2) a seed-data migration that populates all five stance rows with authored content, and (3) a backend update — the RPC function and the stances route response — to surface the new fields to the API consumer.

The schema concern is straightforward but has one critical constraint: `inform.compass_stances` is owned by another Empowered.Vote product (the Inform Pillar), and this project shares the Supabase instance. The migration must use `ALTER TABLE inform.compass_stances ADD COLUMN IF NOT EXISTS` (the `IF NOT EXISTS` guard was already used for `supporting_points` in Phase 3 and is the established safe pattern here). The migration applies via `mcp__supabase-local__apply_migration` — `supabase db push` is explicitly prohibited on this project.

The RPC function `connect.get_stances_for_community` currently returns `(position INT, text TEXT, supporting_points TEXT[])`. It must be replaced with `CREATE OR REPLACE FUNCTION` returning the two new columns as well. Because this function already has an established RETURNS TABLE contract consumed by the stances route, both must change atomically — the RPC update and the route response map must stay synchronized.

The content concern is where most authoring effort lives. The stances model is bespoke: text describes objective policy outcomes, numbers 1–5 are internal handles never shown to users, and stances display in random order per render. `description` (2–4 sentence narrative explaining the stance) and `example_perspectives` (who might hold this view and why, without party labels) must be authored for every stance row of every seeded topic. The correct type for `example_perspectives` is `TEXT[]` — the content is an ordered list of plain strings (persona + reasoning), not structured objects. `JSONB` would add query flexibility this project does not need and would complicate both authoring and the API response shape.

**Primary recommendation:** One migration adds columns; a second migration (or same migration in a seed section) UPDATEs all existing stance rows with authored content. The RPC function is replaced via `CREATE OR REPLACE FUNCTION`. The stances route map adds `description` and `examplePerspectives` to the response object. Tests for the stances endpoint are updated to assert the new fields.

### Pattern 1: Schema Migration with Seed Data in One File

**What:** A single migration file that (a) adds columns with `IF NOT EXISTS`, (b) replaces the RPC function with updated RETURNS TABLE, and (c) UPDATEs all existing stance rows.
**When to use:** When schema and data are tightly coupled (can't have the columns without content that Phase 5 depends on).

```sql
-- Source: established project pattern from 20260416074245_phase3_schema_gaps.sql

-- 1. Add columns to inform.compass_stances
ALTER TABLE inform.compass_stances
  ADD COLUMN IF NOT EXISTS description TEXT,
  ADD COLUMN IF NOT EXISTS example_perspectives TEXT[] NOT NULL DEFAULT '{}';

-- 2. Replace RPC function with updated RETURNS TABLE contract
CREATE OR REPLACE FUNCTION connect.get_stances_for_community(p_community_id UUID)
RETURNS TABLE (
  position              INT,
  text                  TEXT,
  supporting_points     TEXT[],
  description           TEXT,
  example_perspectives  TEXT[]
)
LANGUAGE sql
STABLE
SECURITY DEFINER
AS $$
  SELECT
    s.value AS position,
    s.text,
    COALESCE(s.supporting_points, '{}')        AS supporting_points,
    s.description,
    COALESCE(s.example_perspectives, '{}')     AS example_perspectives
  FROM connect.communities c
  JOIN inform.compass_stances s ON s.topic_id = c.topic_id
  WHERE c.id = p_community_id
  ORDER BY s.value ASC;
$$;

GRANT EXECUTE ON FUNCTION connect.get_stances_for_community(UUID) TO anon, authenticated;

-- 3. Seed authored content for all stance rows
-- UPDATE blocks per topic (once topic_id UUIDs are confirmed from the DB)
UPDATE inform.compass_stances
SET
  description = '...',
  example_perspectives = ARRAY['...', '...', '...']
WHERE topic_id = '<topic-uuid>' AND value = 1;
-- ... repeated for all 5 values × all seeded topics
```

**Note on description nullability:** The success criteria require "non-null description on every row." The column should be `TEXT` (not `TEXT NOT NULL`) at the DDL layer because the shared Inform schema may have topic rows that don't yet have authored content authored by this project. Using `NOT NULL DEFAULT ''` would be technically correct but could silently mask missing content. Use nullable `TEXT` + enforce non-null through seed content + test verification.

### Anti-Patterns to Avoid

- **Omitting `IF NOT EXISTS` on ADD COLUMN:** The inform schema is shared. Another migration could have already added these columns. Always use `IF NOT EXISTS`.
- **Using `CREATE FUNCTION` instead of `CREATE OR REPLACE FUNCTION`:** The function already exists with an older contract. `CREATE FUNCTION` will fail; `CREATE OR REPLACE` replaces it safely.
- **Adding a `NOT NULL` constraint on description without a default and without the seed data in the same migration:** PostgreSQL will reject the ALTER TABLE if existing rows have nulls and no default is specified. Either add the column as nullable and enforce via seed content, or supply a default value alongside the constraint.
- **Forgetting to update the GRANT after `CREATE OR REPLACE FUNCTION`:** Replacing a function with `CREATE OR REPLACE` resets execute permissions in some PostgreSQL configurations. Repeat `GRANT EXECUTE ... TO anon, authenticated` after the replacement to be safe.
- **Hard-coding topic UUIDs without first confirming them from the live database:** The `inform.compass_stances` rows were seeded by a different product team. The UUIDs of topics are unknown to this project; they must be queried before authoring seed content. This is the single most important lookup before writing the UPDATE statements.
- **Setting `example_perspectives` to political party labels or partisan framing:** The stance model explicitly prohibits party labels and partisan framing. All example perspectives must describe values, goals, or circumstances — never party identity.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Cross-schema RPC call | Direct supabase query to inform.* from app code | `connect.get_stances_for_community` RPC (already exists, just update RETURNS TABLE) | The SECURITY DEFINER + connect schema pattern is established; the anon role can't query inform.* directly; replacing the existing RPC is the only correct path |
| Seed data management | Custom script or manual console UPDATEs | SQL UPDATE statements in a Supabase migration (applied via MCP) | Migrations track history, are version-controlled, and apply atomically; manual console changes are explicitly prohibited by project rules |
| Content validation | Runtime null checks at route layer | Authored seed content with non-null values in the migration | The success criteria require no nulls in production data; the right place to enforce this is the data layer, not the application layer |

**Key insight:** This phase is mostly data engineering (authoring and migrating content) with a thin layer of route/test updates. The hardest part is getting the authored content right (neutral, policy-outcome focused, no party labels) — not the technical changes, which are small.

## Common Pitfalls

### Pitfall 1: topic_id UUIDs Unknown Before Authoring

**What goes wrong:** The seed UPDATE statements target specific `topic_id` values and `value` (1–5) pairs. If the UUIDs aren't confirmed from the live database before writing the migration, the UPDATEs will affect 0 rows and silently succeed.
**Why it happens:** `inform.compass_stances` is owned by a different product team. No migration in this repo created those rows. The UUIDs are live-database values unknown to the codebase.
**How to avoid:** Query the live database via MCP before writing seed content: `SELECT id, topic_id, value, text FROM inform.compass_stances ORDER BY topic_id, value;`. Confirm which topic UUIDs correspond to seeded communities, then write UPDATE statements targeting those exact UUIDs.
**Warning signs:** Migration applies cleanly but stance API still returns `description: null` — means the WHERE clause matched 0 rows.

### Pitfall 2: RPC RETURNS TABLE Contract Mismatch

**What goes wrong:** The RPC is updated but the route's TypeScript type annotation for the response still references the old shape (missing `description` and `example_perspectives`). TypeScript compiles but runtime produces undefined fields.
**Why it happens:** TypeScript doesn't automatically infer Supabase RPC return types without generated types; the type is hand-annotated in the `.map()` call.
**How to avoid:** Update both the RPC function AND the inline type annotation in the map at the same time. The map should type the parameter as `{ position: number; text: string; supporting_points: string[]; description: string | null; example_perspectives: string[] }`.
**Warning signs:** `res.body.data[0].description` is `undefined` in tests despite the mock including `description`.

### Pitfall 3: Cache Serving Stale Stance Data After Migration

**What goes wrong:** After the migration adds columns and the route is updated, the stances endpoint still returns the old shape because the 30-minute Redis cache is serving a cached response.
**Why it happens:** `cacheMiddleware(TTL.STANCES)` caches the full serialized response object for 30 minutes. A migration doesn't invalidate the cache.
**How to avoid:** After migration and deployment, either (a) wait for the TTL to expire naturally, or (b) flush the relevant Redis keys. In dev/test, the in-memory store resets on process restart — not an issue. In production, the Render deployment restarts the process which clears in-memory cache; Upstash Redis TTL will expire the old entries within 30 minutes.
**Warning signs:** API response after deployment still missing `description` and `examplePerspectives` fields for up to 30 minutes.

### Pitfall 4: Authored Content Violates Stance Model Rules

**What goes wrong:** Example perspectives use party names ("Republicans believe...", "Democrats support...") or the description frames the stance as "progressive" or "conservative."
**Why it happens:** These are natural language patterns when describing political positions.
**How to avoid:** The stance model rule is "objective policy outcomes, not tribal framing." Use value-based framing: "Someone who prioritizes individual liberty might hold this view because..." or "People who believe market forces are most efficient tend to..." — never party names or partisan spectrum labels.
**Warning signs:** The word "Republican", "Democrat", "conservative", "progressive", "left", "right" appears in any authored content.

### Pitfall 5: `example_perspectives` Array Length Inconsistency

**What goes wrong:** Some stances have 3 example perspectives, others have 2, others have 5. The frontend (Phase 5) expects a consistent number for layout rendering.
**Why it happens:** No schema constraint enforces array length.
**How to avoid:** Choose a consistent count for all stances across all topics (3 is the natural fit for a 3-column layout typical in civic apps). Document the count as a content convention, not a schema constraint.
**Warning signs:** Frontend renders unevenly — some stance cards taller than others due to differing perspective counts.

## Open Questions

1. **How many seeded topics exist in inform.compass_stances right now?**
   - What we know: The inform schema is owned by the Empowered.Vote platform and the Focused Communities repo has no record of what topics or how many stance rows are seeded.
   - What's unclear: The exact number of topics and their UUIDs. Could be 1, could be 20.
   - Recommendation: The planner must make querying the live DB the first task of this phase. `SELECT topic_id, COUNT(*) FROM inform.compass_stances GROUP BY topic_id;` gives the shape immediately. Authoring is blocked until this is known.

2. **Does inform.compass_topics exist and is it accessible?**
   - What we know: The primer references `inform.compass_topics` as a table. The shared instance memory only confirms `inform.compass_stances` columns.
   - What's unclear: Whether `inform.compass_topics` is accessible via the service role key from this project, and whether a JOIN to it in the pre-migration discovery query will work.
   - Recommendation: The discovery query should be attempted with a simple `SELECT * FROM inform.compass_stances LIMIT 5;` first to confirm access, then attempt the topics join. If `inform.compass_topics` is inaccessible, stances can still be identified by their `topic_id` UUIDs matched against the `connect.communities.topic_id` column.

3. **Is description allowed to be NULL in the schema, or must it be NOT NULL?**
   - What we know: Success criteria say "non-null description on every row." But the inform schema is shared and other topic rows may not have authored content from this project.
   - What's unclear: Whether other tools or teams will INSERT new stances that don't have authored descriptions, and whether a NOT NULL constraint would block that.
   - Recommendation: Add as nullable `TEXT` (no NOT NULL constraint) to avoid breaking the shared schema. Enforce non-null through seed data coverage and API-layer fallback (`description ?? ''`). Document this as a content governance expectation, not a DB constraint.
