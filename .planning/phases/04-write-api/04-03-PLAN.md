    **CRITICAL: Fetch mock architecture for authenticated write tests**

    The write endpoints use `requireAuth` + `requireConnected` middleware. When a request hits these routes, the fetch call sequence is:

    1. **JWKS fetch** — `jose`'s `createRemoteJWKSet` lazily fetches keys on first `jwtVerify()` call. The URL contains `.well-known/jwks.json` or the Supabase project URL. Return the test JWKS.
    2. **Accounts API fetch** — `requireAuth` calls `fetch('https://accounts.empowered.vote/api/account/me', ...)`. Return the mock user object.
    3. **Supabase DB fetch(es)** — One or more `postgrest-js` calls via `fetch`. These are sequential and need `mockResolvedValueOnce` chaining.

    **Use a URL-routing fetch mock** (same pattern as `auth.test.ts`):

    ```typescript
    import { describe, it, expect, beforeAll, afterEach, vi } from 'vitest';
    import request from 'supertest';
    import { generateKeyPair, exportJWK, SignJWT } from 'jose';
    import { createApp } from '../../app.js';

    // Mock the rate limiter module BEFORE app import resolves it
    const mockLimit = vi.fn();
    vi.mock('../../lib/rateLimit.js', () => ({
      postRateLimiter: { limit: (...args: unknown[]) => mockLimit(...args) },
    }));

    const app = createApp();

    let privateKey: CryptoKey;
    let publicJwk: Awaited<ReturnType<typeof exportJWK>>;
    let mockJwks: object;
    let validToken: string;

    beforeAll(async () => {
      const { privateKey: priv, publicKey } = await generateKeyPair('ES256');
      privateKey = priv;
      publicJwk = await exportJWK(publicKey);
      publicJwk.kid = 'test-key-1';
      mockJwks = { keys: [publicJwk] };
    });

    // Sign a test JWT (same issuer/audience as real Supabase tokens)
    async function signToken(sub = 'user-uuid-1'): Promise<string> {
      return new SignJWT({})
        .setProtectedHeader({ alg: 'ES256', kid: 'test-key-1' })
        .setIssuer('https://kxsdzaojfaibhuzmclfq.supabase.co/auth/v1')
        .setAudience('authenticated')
        .setSubject(sub)
        .setIssuedAt()
        .setExpirationTime('1h')
        .sign(privateKey);
    }

    afterEach(() => {
      vi.unstubAllGlobals();
      mockLimit.mockReset();
    });
    ```

    **IMPORTANT:** `vi.mock('../../lib/rateLimit.js', ...)` must be at the top level (hoisted by vitest). The `mockLimit` fn is declared above it so each test can control rate limiter behavior via `mockLimit.mockResolvedValueOnce(...)`.

    **Rate limiter mock patterns:**
    - Allowed: `mockLimit.mockResolvedValueOnce({ success: true, remaining: 4, reset: Date.now() + 3600000 })`
    - Blocked: `mockLimit.mockResolvedValueOnce({ success: false, remaining: 0, reset: Date.now() + 3600000 })`
    - For PATCH and GET endpoints: no `mockLimit` setup needed (editing is not rate-limited)

    **Fetch mock helper — URL-routing approach:**

    ```typescript
    // supabase-js uses res.text() not res.json()
    function makeResponse(body: unknown, status = 200): Response {
      const bodyText = JSON.stringify(body);
      return {
        ok: status >= 200 && status < 300,
        status,
        statusText: status === 200 ? 'OK' : 'Error',
        text: async () => bodyText,
        json: async () => body,
        headers: { get: (_name: string) => null },
      } as unknown as Response;
    }

    const ACTIVE_USER = {
      id: 'user-uuid-1',
      tier: 'connected',
      account_standing: 'active',
      completed_onboarding: true,
      display_name: 'Alice',
    };

    const SUSPENDED_USER = {
      ...ACTIVE_USER,
      account_standing: 'suspended',
    };

    /**
     * Create a URL-routing fetch mock.
     * - JWKS requests -> return test public keys
     * - Accounts API -> return accountResponse
     * - All other (Supabase DB) -> consume from dbResponses queue
     */
    function mockRoutedFetch(
      accountResponse: { status: number; body: unknown },
      ...dbResponses: Array<{ body: unknown; status?: number }>
    ) {
      const dbQueue = [...dbResponses];
      vi.stubGlobal('fetch', async (url: string | URL | Request, opts?: RequestInit) => {
        const urlStr = typeof url === 'string' ? url : url instanceof URL ? url.href : url.url;
        if (urlStr.includes('.well-known/jwks') || urlStr.includes('supabase.co/auth')) {
          return new Response(JSON.stringify(mockJwks), {
            status: 200,
            headers: { 'Content-Type': 'application/json' },
          });
        }
        if (urlStr.includes('account/me')) {
          return new Response(JSON.stringify(accountResponse.body), {
            status: accountResponse.status,
            headers: { 'Content-Type': 'application/json' },
          });
        }
        // Supabase postgrest-js call — consume next DB response
        const next = dbQueue.shift();
        if (!next) throw new Error(`Unexpected fetch call: ${urlStr}`);
        return makeResponse(next.body, next.status ?? 200);
      });
    }
    ```

    **IMPORTANT about JWKS routing:** The `jose` library's `createRemoteJWKSet` fetches from the Supabase project URL on first use. Then `requireAuth` calls the same Supabase URL for JWKS verification, then separately calls accounts API. The URL routing function detects JWKS calls by checking for `supabase.co` in the URL (covers both the `.well-known/jwks.json` URL and the Supabase base URL used by jose). The accounts API URL contains `account/me`. Everything else is a Supabase postgrest-js DB call.

    **IMPORTANT implementation notes:**

    1. **Token caching:** Generate `validToken` once in `beforeAll` via `signToken()` and reuse across all authenticated tests. For the non-author test (3d), generate a second token with different sub: `signToken('user-uuid-2')`.

    3. **JWKS caching by jose:** After the first authenticated test fetches JWKS, jose caches it. Subsequent tests may not trigger a JWKS fetch. The URL-routing mock handles this correctly — if jose uses cached keys, no JWKS fetch happens and the mock still works.

    4. **afterEach cleanup:** `vi.unstubAllGlobals()` clears fetch mock. `mockLimit.mockReset()` clears rate limiter mock.

    5. **The ACCOUNTS_API_URL env var** defaults to `https://accounts.empowered.vote` — the URL-routing mock checks for `account/me` in the URL string.

    6. **beforeAll must await token generation:** `validToken = await signToken()` in `beforeAll` block alongside keypair generation.

    7. **For the non-author PATCH test (3d):** The ACTIVE_USER mock still returns `id: 'user-uuid-1'` from the accounts API, but `requireAuth` overrides `user.id` with `payload.sub` from the JWT. So signing the token with `sub: 'user-uuid-2'` means `req.user.id === 'user-uuid-2'`, even though the accounts API body says `id: 'user-uuid-1'`. This is the correct behavior — the JWT sub is the source of truth for user identity. The accounts API confirms session validity; the JWT determines identity.
